## 对“先做中文产物，再做同格式翻译”的判断

方向成立，但“中文产物”应定义为**已审核的中文语义主稿/字段清单**，而不是先渲染一份 DOCX，再把 DOCX 当作英文事实来源。主稿每一字段保留稳定 ID、原文摘录及定位、模板目标、中文定稿、取舍/异常理由；英文逐字段从此已审核中文语义主稿翻译，并继承相同事实 ID 与原文定位。这样把语义选择做一次，避免 CN/EN 各自重复映射；同时保留原文可追溯性，不能用中文译稿代替源证据。

正式技能目前要求 CN 与 EN 都源自同一归一化源事实，禁止从已渲染 CN 输出生成 EN。建议把上面的“中文语义主稿作为受控翻译中间层”作为工程改进评估，而不是在本次执行中私自更改现行规则或绕过门禁。需先做回归验证，证明每个 EN 值仍回连同一原始事实且双语语义一致，再更新规则。

## 建议的最小工程改法

1. **数据模型一次成形**：抽取包只保存源单元及位置；审核中间件保存 `source_fact_id → template_slot_id → zh_value → en_value`，另存字段状态（已映射/源缺失/不可读/冲突/需裁决）。同一个语义决定只审核一次。
2. **中文语义主稿先过内容门**：按模板标签生成可审阅的 CN 结构化稿（含模板顺序和说明行），先检查漏项、错槽、跨栏、说明行、特殊标签例外及逐项来源证据。审核通过后锁定版本/hash，再进入排版。
3. **英文翻译增量执行**：只翻译已锁定中文语义字段，逐字段保留 source fact ID、术语/限定词及证据级别；不重做字段选择，不读取渲染后的 DOCX/PDF 抽取内容。
4. **把 28:52 变成阶段遥测**：每个审核/修错批次记录 `started_at/ended_at`、active seconds、tool/wait seconds、字段数、初始/剩余 blockers、重开次数及输入/输出 hash。审计机器耗时继续自动采集。至少分别计抽取复核、字段映射、中文定稿、翻译、追溯、preflight修复、规则审计、视觉 QA。
5. **小样本 A/B**：以相同源、模板、技能和审核者跑现行流程与新流程，先测 3 个代表型号；比总主动时间、需要人工裁决字段数、遗漏/错槽数、追溯完整率、返工轮数、最终审计失败数。质量指标不得回退，只有时间有稳定下降才扩大使用。

## 限制与环境问题

- 28:52 是抽取完成到审核证据齐备的墙钟间隔，当前记录没有 active-agent seconds，也未把字段映射、翻译、追溯和修错拆开；阶段占比不可计算。
- 首次尝试基准时，裸 `python` 解析到 LibreOffice Python，该解释器没有 `tkinter`，在导入 GUI 识别模块时中止。系统已装 Python 3.12.10，`py -3.12` 可正常导入 `tkinter`；使用它重跑三次均通过。因此本机不缺 Tk，无需另装不兼容的 tkinter pip 包。工程上应明确 MSDS 的 Python 启动器，避免误用 LibreOffice 嵌入式 Python。
- 只有一个型号样本，当前测试不能证明 A/B 后的绝对提速幅度；它足以证明机器的识别、预检、DOCX 写入/审计均为秒级，主要瓶颈必须靠新增人工阶段遥测才能定位。
